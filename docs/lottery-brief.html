Ten million tickets, and the one that must not be handed out twice

The dataset is 400 MB. It fits in memory. So the interesting question was never “how do we search fast” — it’s “how do two people searching the same pattern at the same instant never get the same ticket.”

02

Three layers, three questions

Structure the whole answer as these three. If you only have two minutes, this slide is the design.

Where does it live?

Storage

PostgreSQL, single primary.

Small data, ACID reservations, and one killer feature — see layer 3.

How do we match a pattern?

Search

Split each number into 6 digit columns + a reversed copy.

Prefix → range scan. Suffix → range scan on the reverse. Scattered → bitmap-AND the fixed digits.

How do we hand tickets out without collisions?

Allocation

SELECT … FOR UPDATE SKIP LOCKED plus a short reservation lease.

Concurrent requests get disjoint rows, and nobody waits.

03

The mechanism to nail

Everything else is supporting detail. This is the part the interviewer is actually testing, so slow down here. One SQL statement does the search and the reservation together: 

WITH picked AS (
  SELECT id FROM tickets
  WHERE d5 = 2 AND d6 = 3                -- pattern ****23
    AND (status = 'available'
         OR (status = 'reserved' AND reserved_until <= now()))
  ORDER BY id
  FOR UPDATE SKIP LOCKED                    -- ← the whole trick
  LIMIT :count
)
UPDATE tickets t
   SET status = 'reserved', reserved_by = :user,
       reserved_until = now() + interval '5 minutes'
  FROM picked WHERE t.id = picked.id
RETURNING t.id, t.number;

B’s query stepped over the three rows A had locked and took the next three. Disjoint by construction — neither query blocked, no application lock, no queue, no coordination service.

“Two users hit the same pattern at the same time. A locks the first three rows; B doesn’t wait for A — it steps over the locked rows and takes the next three. The database guarantees they can’t overlap.” — the 20-second version of the whole design

Then: the reservation is a lease, not a lock forever

available → reserve reserved · 5 min → confirm sold

If the buyer walks away, the lease just expires — the WHERE clause above already treats an expired reservation as available, so correctness never depends on a cleanup job. A reaper sweeps expired rows every 30s purely for tidiness.

Belt and braces: a partial unique index (one live reservation per ticket), an idempotency key per request, and a re-check of reserved_by on confirm.

04

Why Postgres and not…

Have the alternatives ready. The point isn’t that they’re wrong — it’s that you weighed them.

OptionReal strengthWhy not the primary
Redis SET NX EX is an atomic per-ticket lease with a built-in TTL not a system of record — still need a durable store behind it. Keep it as an optional lease layer, not the source of truth.
Elasticsearch native wildcard / regexp queries, scales out no row-lock equivalent — you’d bolt Postgres or Redis on for allocation anyway. Overkill for 10M fixed-format rows.
MongoDB findAndModify is atomic per document no SKIP LOCKED: concurrent claimers collide on the same “first” docs and retry, wasting work. Wildcards only index when prefix-anchored.
Precompute every pattern O(1) lookup 1.77M keys to maintain on every ticket change; most never read. Compute on demand + cache the hot ones instead.

Search, in one minute

Secondary to allocation, but be ready to go deep. The trick is to denormalise the number so every pattern shape hits an index.

If they ask for microseconds: keep an in-memory Roaring bitmap per (position, digit) — 60 sets total, ~50–100 MB. A query ANDs the bitmaps for the fixed positions. It’s only a filter: every candidate is still reserved in Postgres, so the bitmap can lag without ever causing a double-allocation.

06

If they push

What if it grows to a billion tickets?

Hash-partition tickets by id or by first digit. SKIP LOCKED works per partition. Reads go to replicas; the primary only carries reservation writes. The in-memory index shards by first digit, scatter-gather.

A user reserves tickets and never buys. Now what?

The lease expires. The allocation query’s WHERE clause already counts an expired reservation as available, so the ticket is claimable again immediately — the reaper job is just housekeeping, not a correctness dependency.

Everyone searches the same popular pattern. Lock contention?

No — that’s the whole point of SKIP LOCKED. Requests touch disjoint rows, so throughput scales near-linearly with concurrent users. There’s no global pattern lock to queue on.

The in-memory index is stale — isn’t that a bug?

It’s advisory only. A stale candidate that’s already taken simply fails the Postgres reservation and gets skipped. Worst case is one wasted reserve attempt, never a wrong result.

Clock skew between app servers?

All lease math uses now() inside the SQL — the database clock, never the app server’s. One clock, no skew.

API pod crashes mid-reservation?

The transaction rolls back. Rows are never left locked; there’s nothing to clean up.

The 30-second version

Store 10M tickets in one Postgres instance — the data’s tiny. Split each number into digit columns so any wildcard shape hits an index. Hand tickets out with a single SELECT … FOR UPDATE SKIP LOCKED + UPDATE: concurrent users for the same pattern get disjoint rows and nobody blocks. Reservations are 5-minute leases that self-heal on expiry. Add an in-memory Roaring-bitmap index and Redis leases only if search QPS demands it — neither can compromise correctness.
